# Testing

The engine is checked from four directions. Every suite runs under `npm test`
(Node's built-in `node:test` via `tsx`; `scripts/run-tests.cjs` finds every
`*.test.ts` under `src/`).

| Suite | Where | What it proves |
|---|---|---|
| Engine unit tests | `src/engine/__tests__/*.test.ts`, `src/__tests__/` | Individual mechanisms (stack, triggers, battle, choices, persistence, redaction, card text parsing, …) behave as `RULES.md` says. Synthetic fixtures only. |
| Per-card suite | `src/engine/__tests__/per-card/<set>.test.ts` | Every catalog card plays its main effect on a small mid-game board, with concrete picks and outcomes. |
| Clause suite | `src/engine/__tests__/clauses/<batch>.test.ts` | Every printed clause of every card does what the printed text says. |
| Rules suite | `src/engine/__tests__/rules/<batch>.test.ts` | Every numbered rule of the Comprehensive Rules v2.5 and every FAQ v2.0 ruling is followed, independent of any real card. |

Run one file while working on it:

```
node --import tsx --test src/engine/__tests__/battle.test.ts
```

## The standard

- **The spec is never the engine.** Card tests take their expectations from
  the card's *printed* text (`markup`, or `data/card-audit/corrections.json`
  where a printing's wording differs from the catalog `text`). Rules tests take
  them from the CR / FAQ (`docs/`, extracted to `data/rule-tests/source/`) and
  the rulings ledger (`data/rule-tests/rulings.md`). `RULES.md` explains how
  the engine represents a rule; where it disagrees with the CR, the CR wins.
  Card text wins over the CR (CR 101.1).
- **A card or rule the engine gets wrong is a failing test**, never a
  weakened assertion.
- **Determinism.** Shuffles, coin flips and random picks use a fresh seed per
  game unless you pass one (`buildGame({ random })`, `setupGame(…, { seed })`).
  A test whose outcome could depend on a roll must pass a seeded / fixed
  `random` (`() => 0.1` to win flips, `() => 0.9` to lose them, or a small LCG
  from `support/prng.ts`). Sweep a few seeds (0, 0.3, 0.99) when the outcome
  could depend on one. A flaky test is worse than none.
- **Every `assert.ok(x)` / `assert(x)` has a message.** Without one, a failing
  `assert.ok` makes Node re-read and parse the test file to quote the
  expression, which can hang on the very large test files. The clause and
  rules gates reject message-less calls.
- **Every refusal is checked for the right reason** with `refused(fn, why,
  pattern?)` (`_clause.ts` / `_rule.ts`), never a bare `assert.throws`, and is
  paired in the same test with a positive control that differs only in the
  condition under test. A bare throw check also passes on "It is not your
  priority", an unknown id or a `TypeError`.

## Clause suite

### How it works

- **Rules groups.** Printings of one name that are identical in everything the
  engine reads (`markup`, behavior, cost, stats, FLIP UP, …) form one group,
  tested once through any of its printings. The grouping lives in
  `src/engine/__tests__/clauses/_manifest.ts`.
- **Clauses.** Each group's printed markup is split into clauses: a keyword
  (`0:kw:COVERT`), Unique (`0:unique`), Attach to (`0:attach`), a rules
  paragraph (`1:rule`, threshold-gated `1:rule@oooo`, named
  `0:rule:STARTING DRAW`), an ability (`2:ability:<ref>`), an option
  (`3:option:OPTION 1`), each paragraph of a grant (`2.0:grant-ability`),
  `flipUp`, `provides`, `fealty`, `extraCost` / `effect`. A card with no rules
  text has `vanilla`. Clauses are grouped into batches of about 40.
- **Manifest.** `data/card-tests/clauses.json` is generated by
  `npm run card-tests -- build` and checked by the gate.
- **Markers** (`_clause.ts`):
  - `clause(printingId, key | keys, title, fn)` — a test that the engine does
    what the clause says.
  - `clauseMismatch(printingId, keys, findingId, title, fn)` — the same test
    for a clause the engine gets wrong. It asserts the printed behavior and
    **fails** until the card is fixed; the finding id ties it to a write-up in
    `data/card-tests/findings/<batch>.md`.
  - `clauseUnimplemented(printingId, keys, reason, title, fn)` — only for
    printings whose fidelity is `stub` / `partial` (`data/card-fidelity.json`;
    today the two Showdown factions). Runs as `todo`.
  - `exempt(printingId, keys, reason)` — a clause with nothing for the engine
    to do (deck construction, tournament legality).
- **Gate.** `clauses/_coverage.test.ts` checks that the manifest is current,
  every reference names a real printing and clause, every mismatch is written
  up, `clauseUnimplemented` appears only on stub / partial printings, every
  batch in `data/card-tests/done.json` covers all its clauses, and there are no
  bare asserts.
- **CLI** (`npm run card-tests -- <command>`; the full list is at the top of
  `scripts/card-tests/cli.ts`):
  - `build`, `batches`, `manifest <batch> [--missing]`, `show <printingId>`;
  - `coverage [--batch b]` (writes `data/card-tests/progress.md`),
    `mark-done <batch>`;
  - `report [--batch b]` runs the clause tests and lists broken cards
    (written up, then unexplained), mismatch tests that now pass, and
    unimplemented clauses; `status`, `findings`, `close <findingId>`;
  - `mutate --batch b --file muts.txt` **tests the tests**: it applies each
    data mutation to the catalog in memory and counts new failing tests. A
    line is `label|||<js>` with `cards` and `card(name, set?)` in scope, e.g.
    `card("Compulsive Creeper","Open Beta").behavior.abilities[0].modifiers[0].value = 2`.
    *detected* = new failures (or a hang); *SURVIVED* = a test is missing;
    *FIXES n recorded mismatch* = the mutation turned a mismatch green (a hint
    at the real fix); *ERROR* = the mutation didn't apply. A mutation of a
    field the engine never reads is a silent no-op, not a survivor. The hook is
    in `scripts/card-tests/mutation/`; nothing on disk changes.

### Multiplayer inventory

`npm run card-tests -- mp-inventory` writes `data/card-tests/mp-inventory.json`
and a human-readable `mp-inventory.md`. It reuses the manifest's rules groups
and clause keys (`clauses/_mpInventory.ts`), so it joins 1:1 with
`clauses.json` by (group id = a printing id, clause key). Per clause:

- **`phrases`**: every printed player phrase in the clause's printed text (the
  same text as `Clause.text`: `markup`, which is generated from
  `corrections.json` where a printing's wording differs): `text`, `category`,
  `at` (offset in the clause text), `reminder: true` inside reminder
  parentheses. The matcher is case-insensitive, folds curly apostrophes, and
  gives each piece of text to the most specific pattern (`PATTERNS` in the
  module): `yourOpponent`, `bothPlayers`, `anOpponent`, `eachOpponent` (each /
  every / all / your opponents, plural), `eachPlayer`, `anyPlayer`,
  `anotherPlayer`, `activePlayer`, `seat`, plus the singular `opponent` forms the
  spec left open: `anyOpponent`, `thatOpponent`, `theirOpponent`, and
  `opponentBare` (any other singular "opponent", e.g. "the opponent's"), and
  `eachOtherPlayer`, `eachOfYou`, `thatPlayer` (that / those / the / picked player),
  `xPlayers`, `eitherDeck`, `playersBare` ("Players can attack…"), `playerOther`
  (fallback; empty today).
- **`behavior`**: every player word in the behavior data: a string in a
  player-valued field (`PLAYER_FIELDS`) whose value is `opponent`, `self`, `any`,
  `controller`, `owner`, `activePlayer`, `anyPlayer` or `all`; a PlayerRef object
  (`ownerOf`, `controllerOf`, `player`); and an effect that iterates over players
  (`forEachPlayer`, `anyPlayerMayPay`, `alternatingPay`, `otherPlayerChooses`,
  `auctionForCard`, `partitionAndPick`, `separateIntoPiles`, `useAnyAbility`). Each
  has its JSON `path` from the card, `value`, the `unit` it sits in (an ability
  or another behavior field) and how it reached the clause (`link`). The
  manifest has no ability-to-clause mapping, so: an ability a clause names with
  `ref` maps to that clause (`ref`); `flipUp` data to the FLIP UP clause and
  `thresholdSlack` to FEALTY; any other (unlinked) data is listed on the only
  clause it could belong to (`exclusive`) or on every clause it could belong to
  (`shared`, with `sharedWith`). Count a `shared` word once per path.
- **`mp`**: `true` if `phrases` or `behavior` is non-empty; `"quantified"` if a
  phrase is `eachOpponent`, `eachPlayer`, `eachOtherPlayer` or `eachOfYou`.

`mp-inventory.md` has the counts per category and per set and a preliminary
mismatch list (printed phrase vs data word). It is input for reclassifying card
data, not a gate. `mp-inventory.test.ts` regenerates both files in memory and
fails if either is stale, if the join with `clauses.json` breaks, or if the
behavior data holds a player word in a field `PLAYER_FIELDS` doesn't read. After
changing the catalog or the matcher, rerun the command.

### Multiplayer vocabulary gate

`mp-vocabulary.test.ts` keeps the card data's player words honest against the
multiplayer spec (`data/card-tests/mp-spec/<set>.json`, format and meanings in
its `README.md`) and gives the Phase 4 agents their work queue,
`data/card-tests/mp-worklist.json`. The logic is in `clauses/_mpWorklist.ts`,
shared by the gate and by `npm run card-tests -- mp-worklist` (regenerates the
worklist, prints pending sites and clauses per set, and lists anything the gate
would reject). A site is a spec `dataChanges` entry: card (rules group), clause
key, behavior `path`, recorded `now`, `meaning`, `edit`. Paths are read against
the group's representative printing.

What it asserts:

- **Inventory is current**: `mp-inventory.json` equals a fresh `buildMpInventory()`.
- **Spec covers data**: every inventory behavior site whose word is not plain
  `self` / `controller` / `owner` / `ownerOf` / `controllerOf` has a `dataChanges`
  entry on the same clause at the same path. A new site fails, naming card,
  clause and path. Spec entries must name a clause the inventory has.
- **`edit: false` sites stay put**: each still holds its `now` (a `forEachPlayer`
  matches by type). A shared copy of a site that another clause owns with
  `edit: true` is judged by the owner's entry. Change the data back, or update
  the spec.
- **Pending queue**: an `edit: true` site still holding its `now` is pending;
  `mp-worklist.json` must list exactly the pending sites, grouped by set (card,
  clause, path, `now`, target meaning), so the gate fails after a data or spec
  change until `mp-worklist` is rerun. A site whose `now` is not a stored value
  (`null`, `[]`, prose, or an object such as a `forEachPlayer`) carries a
  `snapshot` in the worklist, a hash of the site's own keys and scalar fields
  (nested nodes ignored), and is pending while that is unchanged.
- **Valid target form**: an `edit: true` site that left its `now` must hold a
  valid form for its meaning (`MEANING_FORMS`, from the plan's "Player
  vocabulary"). It is judged only when `now` is a player word (`"opponent"`,
  `"self"`, ...) or `forEachPlayer`: `anyOneOpponent` becomes `"opponents"` (in a
  selector, scope or condition), a `controllerOf` / `ownerOf` ref or a
  `chosenPlayer` ref; `eachOpponent` becomes `"opponents"` (an effect's
  `player`, a selector or a scope; never a `chooser` or a target's `player`) or
  the site sits inside `forEachPlayer { players: "opponents" }`; `chosenPair` a
  `forEachPlayer` with `players: "pair"`; `refersBack` may read `"acting"` in an
  `opponentFrom: "acting"` ability; and so on. The accepted forms per meaning
  are listed in `data/card-tests/mp-spec/README.md` ("Target forms the gate
  accepts"). Sites whose `now` is a flag, restriction name or described new
  shape are done once they differ, except an `opponentFrom` site, which must
  hold `"acting"`.
- **Printings stay in step**: every printing of a rules group holds the
  representative printing's behavior, faction and flip-up data, so a patch
  reaches the reprints in other sets.

Paths are exact. A structural edit that moves a site (inserting a step before
it, wrapping it in an iteration) makes the old path stale: an `edit: false`
site there fails, and an `edit: true` site whose path vanished fails unless an
enclosing `forEachPlayer` carries the right `players`. Update the spec's paths
in the same change, then rerun `mp-inventory` and `mp-worklist`.

### Rules for writing clause tests

1. **Expected behavior comes from the printed text** (the manifest's markup /
   plain text) and `RULES.md`. Never take it from the behavior JSON, the
   archival `text`, or existing tests, which can encode the engine's mistakes.
   Engine data (ability ids, declaration ids, choice kinds) is only for
   *driving* the engine.
2. **Every sentence of a clause is asserted somewhere.** A test that would pass
   even if the clause were implemented wrong is not a test.
   - **Costs.** Each cost is actually paid (ready resources before and after,
     the source depleted, the cards discarded or destroyed). One refusal test
     per "Use/Play this only if/while/during …" restriction and per
     unaffordable cost.
   - **Targets.** Everything the text lets you pick can be picked; everything
     it excludes is refused: wrong type, wrong controller, wrong zone,
     "other", attacking / blocking / depleted, subtype or name restrictions.
   - **Effects.** Every observable result: zones, stats (`engine.getStat`),
     damage, tokens, influence, hand / deck / discard contents and order,
     depleted state, control. "May": accept *and* decline. "If you do /
     otherwise": both branches. X: at least two values (and 0 where legal).
     "Each / all / your / opponent's": include a card that must *not* be
     affected. "Up to N": N and fewer. Every deck search shuffles that deck
     afterwards (CR 312.1), even when it finds nothing — assert it.
   - **Durations** end. **Triggers** fire on the event and not on a near miss
     (the other player's turn, another card, the wrong zone).
   - **Static rules**: on while the condition holds, off when it doesn't, and
     off again once the card leaves play. Check scope (yours / theirs /
     "other" / the card itself).
   - **Replacements / preventions**: the original event doesn't happen; the
     replacement does.
   - **Threshold-gated rules**: active with the icons, inactive without.
   - **Keywords** (`RULES.md` §9): COVERT can't be blocked by non-covert (use
     the `_battle.ts` checks); TACTICAL deploys whenever a tactic could; AGGRO
     attacks the turn it enters; UNIQUE X as `RULES.md` describes; ATTACH TO X
     attaches to X and is refused for a non-X host.
   - **FLIP UP**: flips for exactly the printed cost and threshold, refused
     when short. A non-tactic is also refused inside an opponent's response
     window (`declareAttackOpenWindow`; CR 507.4d). The cost is paid before
     flipping, so the card may help pay it; the threshold is checked after, so
     its own icon doesn't count.
   - **PROVIDES**, **FEALTY**, each **option** separately, **grants** through
     the recipient, **vanilla** (deploys at the printed cost and threshold,
     refused one short, printed stats in play).

   2½. **Expected numbers are literal printed values** ("cost 3 · str 2 /
   spd 2 / life 1"), never `printing(id).strength`; a test comparing the
   engine with the card's own data can't catch wrong data.
3. **Use the exact printing** (`printing("<id>")`). Other cards on the board
   are synthetic (`character()`, `item()`, `bank()`, …) unless the text names
   a card.
4. **Phantom engine data is a finding**: an ability, keyword, FLIP UP, cost or
   restriction with no printed counterpart.
5. **When a test fails:** first re-check that the test drives the engine
   correctly and expects what the card says. If the engine really differs,
   switch to `clauseMismatch` and write the finding; never weaken or delete
   the assertion. If the engine can't express the situation at all, assert the
   printed behavior as far as the API allows and file it as `unimplemented`.

   5½. **Ambiguous sentences are still tested**, using the most literal
   reading. If the engine fails it, file the mismatch with category
   `rules-question` and name the alternative reading.
6. **`exempt` only** for text with no engine behavior at all, always with a
   reason.
7. **Files.** One file per batch (or `<batch>.<part>.test.ts`) with top-level
   `clause(...)` calls, no `describe`. Printing ids, keys and finding ids are
   string literals or same-file `const`s — the coverage scan reads them
   statically, so a `for (const ID of [...]) clause(ID, …)` loop is invisible
   to it. Write one body function and give each printing its own literal call:
   `clause(A, "0:rule", "…", body(A)); clause(B, "0:rule", "…", body(B));`
8. **A batch is done** when every failing test is a written-up
   `clauseMismatch`, `coverage --batch <b>` shows nothing missing, and
   `mark-done <b>` succeeds.

### Finding template (`data/card-tests/findings/<batch>.md`)

```
### <batch>-<n> — <Card>: <one-line summary>
- Printings: <id> (<set>), …
- Clause: `<key>` — <printed clause>
- Category: data | engine | unimplemented | rules-question
- Expected (printed): …
- Actual: …
- Suspected cause: … (Root cause: SYS-n if known)
- Test: src/engine/__tests__/clauses/<batch>.test.ts ("<test title>")
```

Once the card is fixed, `npm run card-tests -- close <findingId>` checks that
every citing test passes and turns its `clauseMismatch` calls into `clause`.

## Rules suite

### How it works

- **Atoms.** The CR is split into one atom per numbered rule or sub-rule
  (`CR 408.3b`) with its unnumbered paragraphs and examples folded in; each FAQ
  Q&A is one atom (`FAQ 7`). Title-only headings (`CR 201.1 Name`) are
  `kind: "heading"` and need no coverage. `data/rule-tests/atoms.json` is
  generated from the committed source text (`data/rule-tests/source/`) by
  `npm run rule-tests -- build` and checked by the gate.
- **Batches.** `BATCHES` in `rules/_atoms.ts` groups the CR sections, the FAQ and the
  multiplayer atoms (`source/multiplayer.txt`, each citing the rulings in
  `rulings.md` it rests on: `RQ-n` and `MPQ-Pn`) into 13 batches. A batch's files are `rules/<batch>.test.ts` (or
  `<batch>.pN.test.ts`).
- **Markers** (`rules/_rule.ts`). Every rule atom must be named by one of:
  - `rule(ids, title, fn)` — a test that the engine follows the rule(s);
  - `ruleMismatch(ids, findingId, title, fn)` — the same test, known failing,
    with `## <findingId>` written up in `data/rule-tests/findings/<batch>.md`;
  - `ruleOpen(ids, "RQ-n", title, fn)` — a `todo` test for a rule the sources
    leave open, written up in `data/rule-tests/questions/<batch>.md` and
    listed in `data/rule-tests/QUESTIONS.md`;
  - `ruleExempt(ids, reason)` — nothing for the engine to do (policy, physical
    layout, a definition fully covered by other atoms).

  One test may name several atoms; one atom usually deserves several tests
  (positive, negative, boundary).
- **Gate.** `rules/_coverage.test.ts`: the manifest is current, every reference
  names a real atom, every mismatch and open question is written up, every
  exemption has a reason, every batch in `done.json` covers all its atoms, no
  bare asserts.
- **CLI** (`npm run rule-tests -- <command>`): `extract` (re-extract the source
  text from the PDFs in `docs/`; needs `pdftotext`), `build`, `batches`,
  `manifest <batch>`, `show "<id>"`, `coverage [--batch b]` (writes
  `data/rule-tests/progress.md`), `mark-done <batch>`, `report`.

### Writing rules tests

1. `npm run rule-tests -- manifest <batch>` and read every atom's full wording.
2. Write the scenario list from the wording alone: for each atom, the positive
   case, the negative case, and the boundary (0, 1, exactly enough, one too
   few, both players, active vs non-active). Examples printed in the CR become
   tests verbatim.
3. Then write the tests, reading the engine only to learn how to drive it. If
   the engine disagrees with the wording, that is a `ruleMismatch`.
4. If the wording is ambiguous, or `RULES.md` and the CR disagree, file an
   `RQ-n` with a `ruleOpen` test; don't pick a reading.
5. Tests use synthetic fixtures (`support/fixtures.ts`, `buildGame`,
   `createTwoPlayerFactionGame`), never the real catalog (`data/cards/`). They must **not**
   import `_clause.ts`, which auto-answers some prompts: a rule test sees every
   prompt and answers it itself.

Findings format (`data/rule-tests/findings/<batch>.md`):

```
## RF-<batch>-<n>: <one-line summary>
- Atoms: CR 408.3b
- Test: rules/<file>.test.ts "<title>"
- Wording: "<the rule's words that the engine violates>"
- Engine does: <what happens>
- Cause: <file/function if known>
```

## Random-play driver and replay digests

A fifth check, aimed at "did two-player behavior change?" rather than at any one
rule. `replay-2p.test.ts` replays a committed corpus of seeded random games and
compares a digest of the rules state after every action.

- **Driver** (`support/driver.ts`, decks in `support/random-decks.ts`).
  `playRandomGame(setup, driverSeed)` plays a game to the end by choosing
  uniformly (weighted towards progress: attack, end turn, pass) among legal
  actions. It reads only the engine's public queries (`getFlowView` for the mode
  and the acting player, then `getPlayableHandCards`, `getPlayRequirements`,
  `getPaymentOptions`, `getActivatedAbilityStatuses`, `getFlipUpPlayability`,
  `getAttackOptions`, `getBlockOptions`, `getSelectionRequirements`, the setup
  choice queries, and each pending choice's own fields) and runs every candidate
  through `engine.checkAction` before `perform`. Decks are seeded random legal
  Constructed decks from the real catalog (full-fidelity printings only, checked
  with `findDeckConstructionIssues`), built by `createTwoPlayerFactionGame`. The
  action log and the setup (`GameSetupInputs`: seed, decks, who goes first, staple
  choices, created ability) are plain JSON; same setup + same driver seed + same
  catalog gives the same game. `perform` writes into the action it is given, so
  the driver (and the replay) hand the engine a copy and keep the pristine one.
  Two things are reported as findings, never worked around: `perform` throwing on
  an action `checkAction` approved, and a non-`gameOver` state with no accepted
  action (a query throwing while candidates are listed is reported too).
- **Digest** (`support/digest.ts`). `digestState(state)` is the first 16 hex
  characters of the SHA-256 of the canonical JSON (sorted keys, `undefined`
  dropped) of `projectForDigest(state)`. The projection is `GameState` minus
  `gameLog`: the log is narration (wording, per-viewer redaction text) that no rule
  reads. Any further exclusion goes into `projectForDigest`, with its reason, and
  nowhere else.
- **Corpus** (`data/replays/2p/game-NNN.json`, `index.json`). Per game: setup,
  actions, the digest after setup and after each action, and the action counts at
  which the test saves the game, pushes it through JSON and loads it back before
  carrying on (`roundTripAfter`). `index.json` is informational: totals, which
  sets and factions are covered, the seeds that were skipped, and the save/load
  points that did not work (see below). The test also checks that at least 100
  games are present and that every set and every full-fidelity faction appears.
- **Re-recording**: `npm run record-replays` (flags `--games`, `--jobs`,
  `--max-actions`; defaults 120 / cores-2 / 700, the committed corpus was recorded
  with `--games 104 --max-actions 450`, which keeps the replay test near 45 s of
  CPU and the corpus near 3 MB). Slot `g` plays factions and featured sets picked
  from `g`, so any large run covers all of them. A seed that hits a finding or
  does not finish within `--max-actions` is skipped and listed in `index.json`;
  every recorded game is replayed from its JSON before it is written.
- **When re-recording is legitimate**: only for an intended, explained change to
  two-player behavior (a rules fix, a data fix that alters a card's play), and the
  commit that re-records says which behavior changed and why. A replay test that
  fails after a refactor, a multiplayer change or a performance change is a
  regression: fix the code, not the corpus. Changes to the driver or the deck
  builder also change the corpus; they are not a reason to hide a behavior change
  in the same commit.
- **Save/load points**: a game is saved only where a save -> JSON -> load continues
  to the recorded digests for the next 40 actions; the recorder searches forward
  from 25 / 50 / 75 % of the game for such a moment. A save works at any moment,
  mid-resolution included: what the engine carries between actions
  (`GameState.engineMemory`: the trigger queue, last-known information about departed
  cards, the resolution contexts parked frames share) is part of the state, and nothing
  in the state is reachable by two paths: a context several parked frames and the open
  choice share is held once, by id. The committed `index.json` lists 41
  `roundTripFailures` from before that was so; they are pinned by
  `regressions/save-load-round-trip.test.ts`, which also sweeps the corpus (a
  deterministic sample of games and mid-resolution moments; `SAVE_LOAD_SWEEP=full` tries
  every one), and `regressions/state-has-no-aliases.test.ts` scans every state of a
  sample of games for shared objects (`ALIAS_SCAN=all` scans every game).
  `projectForDigest` leaves `engineMemory` out because it did not exist (it was
  engine-instance memory) when the corpus was recorded, except the parked frames'
  contexts, which it puts back inline as recorded.

## Engine-driving notes

These apply to every suite.

- **Battles.** After `declareAttack` the attacker holds priority; pass it
  (`resolvePendingResponses`, or `declareAttackBy`) so the defender can respond
  or block. `declareAttackOpenWindow` leaves the defender holding priority. A
  finished battle stays in phase `"finished"` until `advanceFlow`.
  `autoResolveBattle` stalls silently on trigger-order prompts — use `fight` /
  `fightThrough` / `finishBattle`; its custom splits must return `[]` for a
  zero-strength source, and its `legalTargets` are objects
  (`{ type: "card", cardId }`). Battle survivors are depleted afterwards.
  `getBattleView().damageSources` lists only the acting player's sources.
- **`buildGame` boards.** Keys must be unique (a duplicate silently replaces
  the earlier card). Every placed character is attack-eligible unless
  `attackEligible: false`. Face-down cards count as Volition resources, so
  leave them out of "one resource short" boards. Spent resources stay
  attached. Preset `damage` isn't "damage this turn" — inflict it with a real
  effect for "has received damage this turn".
- **`activate` / `play` stop at the first pending choice** and return before
  the effect resolves. Answer the choices (`drain` / `answerPending`) and
  assert `engine.state.pendingChoice` is gone before checking outcomes.
- **`drain()` closes response windows** (it calls `resolvePendingResponses`
  after every answer); to stay inside a window, call `engine.perform`
  yourself.
- **`declineAll` is not always a decline.** It answers `chooserSelectsOption`
  with index 0 (often ACCEPT on "you may … / decline" prompts) and
  `chooserSelectsTarget` with an empty pick (which throws for a mandatory
  pick). It also hides a choice that shouldn't have been offered at all:
  "should NOT trigger" tests assert `engine.state.pendingChoice` is undefined.
- **Two copies of one trigger** raise `orderTriggers` before anything else;
  custom answer functions must handle it.
- **Pending choices don't list their candidates.** Test "can't pick X" by
  trying the illegal pick under `refused(...)`, paired with a legal pick that
  succeeds.
- **`playCard` refusals all read "cannot be deployed right now"**, so the
  message says nothing; every refusal needs a positive control.
  "Activated ability not found" is the right refusal for a suppressed ability
  (pass `/Activated ability not found/`).
- **Costs vs effects.** A printed COST / EXTRA COST is paid when the card or
  ability is played, before responses. Assert it with `playRaw` (or `activate`
  before draining) while the window is still open.
- **"Play / Deploy only if …"** conditions are cleanest through
  `engine.getCardPlayability(...)`, which checks timing, threshold and cost
  only (not targets or extra costs).
- **Target shapes differ by card.** Some abilities take picks up front
  (`targets` on `activateAbility` / `playCard`), others ask through a later
  `chooserSelectsTarget`. Check `npm run card-tests -- show <id>`.
- **The non-active player** can only use abilities inside a response window
  (e.g. on their opponent's attack: the attacker attacks and passes, then they
  act). You can never respond to your own action (CR 607.1).
- **Failed actions can leave partial state.** If `perform` throws, build a
  fresh board for the next assertion.
- **A card that has left play reads printed values** through `getStat`;
  assert zones instead. `moveCard` (private; reach it through `buildGame`
  placements or real actions) clears `faceDown`. `removeFromGame` on a
  discard-pile card does nothing.
- **"did not converge"** from `resolvePendingResponses` means the engine
  soft-locked — a bug, not a test problem.
- `getAvailableActivatedAbilities(playerId)` lists every card's abilities;
  filter by `cardId`. Develop state: `engine.state.developsUsedThisTurn`;
  `canDevelopNow` is false while a battle or prompt is open.
- **TypeScript narrowing.** After `assert.equal(engine.state.battle,
  undefined)`, TS keeps the narrowing; read later state through a function
  (`battleOf(engine)`).
- **Synthetic extra costs.** "Pay N" is numeric (CR 406.3) and interacts with
  cost reductions; use non-numeric costs (`loseInfluence`, `discard`) for
  synthetic helper cards.
